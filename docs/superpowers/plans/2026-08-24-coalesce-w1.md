# Coalesce the W1 read in `webgpu.html`

**Status: implemented, verified, measured — the prediction is wrong.** The change
is committed. Correctness passed (bit-identical output, both modes), but the A/B
shows **no timing change**: 3.24 → 3.26 ms fused, 3.32 → 3.33 ms per-layer, both
inside the noise. The memory-amplification diagnosis is off the critical path at
batch-1. Full write-up:
[`2026-08-24-coalesce-w1-ab.md`](../../measurements/2026-08-24-coalesce-w1-ab.md).
The predictions below stand as recorded, and were scored against the measurement.

## Why

`webgpu.html` measures **3.27 ms** against LiteRT.js's **1.61 ms** on the same
device and browser ([data](../../measurements/2026-08-24-stock-chrome-litert-vs-webgpu.md)).
The repository had no explanation for the gap. Reading the shader gives one.

`W1` arrives from the `.tflite` as `[128][2352]` — output-major. The fused
kernel's inner loop was:

```wgsl
let base = t * 2352u;
for (var i = 0u; i < 2352u; i = i + 1u) {
  acc = acc + w1[base + i] * input[i];
}
```

At step `i` the 128 lanes of the workgroup read `w1[0*2352+i]`,
`w1[1*2352+i]`, … `w1[127*2352+i]` — addresses **9,408 bytes apart**. Nothing
coalesces. Every lane costs its own memory transaction, each fetching a full
cache line to use 4 bytes of it, so reading a 1.2 MB matrix moves on the order of
**19 MB**. The `per-layer` mode had the identical loop.

## What was changed

1. `createEngine` transposes `W1` from `[128][2352]` to `[2352][128]` once at
   upload, off the timed path.
2. Both `FUSED_WGSL` and `LAYER1_WGSL` index it as `w1[i * 128u + t]`, so
   consecutive lanes read consecutive floats — one coalesced burst per step.

Both modes were changed together deliberately: the variable under test between
`fused` and `per-layer` is **dispatch count**, so their memory layout has to
match or that comparison stops meaning anything.

**The arithmetic and its order are untouched** — only addressing changes — so
outputs should be **bit-identical** to before. That is the correctness check:
same digit, same confidence, not merely a plausible-looking result.

## Done

1. **Verified correctness.** ✅ Fixed synthetic input through
   `window.__engine.run` returned **bit-identical** float32 output for new vs old
   in both modes (and fused == per-layer within a build). An injected "1" stroke
   through the real preprocess predicts 1 at 100.0% on all four configs, matching
   `index.html`. Bit-identical, not merely "still predicts 1".
2. **A/B'd on the device.** ✅ `git show 36516e9^:webgpu.html > webgpu-old.html`,
   served locally over `adb reverse`, driven over the DevTools protocol
   (`adb forward tcp:9222`, injected stroke, `#result` readout), 3 sessions × 5
   samples × `timing_runs=1000`, fixed-perf on, Chrome force-stopped between
   sessions. **Result: no change** — see the measurement file. `webgpu-old.html`
   deleted afterwards.
3. **Occupancy is now the moot branch, not the next one.** The gap did *not*
   close, so per the plan's own logic occupancy is still worth considering — but
   it cannot explain a gap that survives a memory-layout fix, and the `MAP_READ`
   round-trip is the better next suspect. Do not chase `dispatchWorkgroups` count
   until the readback path is ruled in or out.

## Prediction, to be scored against the measurement

Coalescing should remove most of the memory amplification. If the ~1.6 ms that
LiteRT achieves is the round-trip floor, the hand-written page should land near
it. **Predicted 1.6 – 2.0 ms, from 3.27 ms.**

If it does *not* improve, the coalescing diagnosis is wrong and the gap is
somewhere else — most likely the `MAP_READ` buffer reuse
([hypothesis](../../architecture.md#what-the-diagrams-could-not-have-told-you)),
which the heap data showed is not an allocation-volume effect.
